## 3. 固定场景与进程放置

| 对象 | 节点 | 正常布局 | 降级布局 |
|---|---|---|---|
| EDP0，故障副本 | SL3061 | dense TP4×DP2；expert ETP4×EP2，8 卡 | dense TP2×DP2；expert ETP2×EP2，4 卡 |
| EDP1，健康副本 | SL3060 | dense TP4×DP2；expert ETP4×EP2，8 卡 | 保持原布局 |

一次运行：正常 → EDP0 四卡同时故障并缩容 → 降级服务 → 四卡回归并扩容 → 正常。故障坐标为 EDP0 的 `(etp, ep)=(0,0),(1,0),(0,1),(1,1)`。启动时根据配置和真实进程组顺序计算、打印 rank；不得使用旧方案的全局 rank 0/1/4/5 常数。记录 `(node, GPU UUID, replica, ep, etp, old_rank, new_rank, world_epoch)`；稳定设备标识与临时 rank 分离。

每个 EP 保留原专家归属。存活卡在各自 EP 内分配新 TP2 local rank，使实际可复用权重字节最大；并列时按稳定设备顺序确定。最终校验 PyTorch 进程组实际 rank 顺序，不能只相信计划中的列表顺序。

| 进程 | 所在节点 | 生命周期与职责 |
|---|---|---|
| 控制器 / 注入器、独立 TCPStore 服务 | SL3060 | 整次 launch 存活，不属于被 kill 的 worker；管理事件、epoch、时间线和控制消息 |
| 节点监管器各一个 | SL3060、SL3061 | 各管理本节点本次 launch 的 worker PID；SL3061 执行目标 kill 与重新拉起；不跨节点代替本地监管器 spawn |
| EDP1 原始 8 个 worker | SL3060 | real 的 16→12→16 world 中持续存活，保留原 CUDA 张量 |
| EDP0 存活 4 个 worker | SL3061 | 跨两个重建阶段持续存活，保留源权重 |
| EDP0 故障 4 个 worker | SL3061 | real 中 kill -9 退出；显存回收完成后由本机监管器启动新 PID；emulate 中 PID 存活但状态释放、数据通路隔离 |
| 每节点一个主机库 owner（Step 3 引入） | 各自节点 | CPU 进程，整次 launch 存活，持有唯一共享 mmap；不随 worker 故障退出 |

real 每轮独立 launch，进程组、worker 和控制服务按轮建立及清理；Step 1 的 20 次也是独立 launch。emulate 一次 launch 连续 `--rounds`，默认 5；每轮开始恢复正常 TP4 并校验权重。报告输出每个 PID 的节点、角色、启动/退出时间、退出原因、替代 PID、epoch 和 GPU UUID。

## 4. 双故障路径及 MPS、回收约束

两条路径共用选源、迁移、KV、服务驱动、注入器和统计，仅故障层接口 `fail(ranks)` / `rejoin(ranks)` / `current_world()` / `rank_map()` 不同。

2026-10-17 用户补充授权：Step 1 增加默认关闭的 `--allow-foreign-gpu-processes`，允许与其他任务共享 GPU，仅用于正确性和可行性判断。此模式记录 foreign 进程，按本测试 PID 消失且进程显存归零确认回收，不要求整卡空闲或显存回到基线；worker 身份、kill 范围和正确性检查保持不变；共享模式允许 foreign MPS 客户端，无法定位的 daemon 管道记录后跳过查询，本测试 worker 必须在内部确认独立 GPU context。结果标记 `shared_gpu_mode=true`，耗时不作正式数据；默认独占模式及正式验收口径不变。详见 [共享模式说明](Step1_共享GPU正确性模式.md)。

- emulate：可预建所有需要的通信组；故障卡释放权重/KV，源目标均为 None。存活 CPU 控制进程可参与控制，但失败 GPU 不参与任何数据发送、接收和占位 ring。回归为 `src=None`、TP4 空目标。
- real：外部注入器指示 SL3061 监管器 kill -9；通过 SL3060 TCPStore 通知存活进程，不依赖 NCCL watchdog 检测。必须 abort 旧通信器，以新 store 前缀重建 12 rank world；回归再重建 16 rank world。不得用预建旧组假装完成重建。
- real 世界重建允许 EDP1 短暂停顿，完整记录暂停；emulate 的 EDP1 应独立持续推进。两种语义区别必须反映在结果中。
- 新 real worker 从主机库读取 TP4 结构与元数据，创建空接收目标；权重由公共迁移计划填充，不能预加载完整权重后仍声称迁移。
- 启动前记录两节点 MPS server/client 列表。SL3060 存在常驻 MPS，不能停止、重启或修改该服务。仅给本任务 worker 设置独立、无服务的 `CUDA_MPS_PIPE_DIRECTORY`，并在 CUDA 初始化后复查，确认 PID 不在 MPS 客户端列表；原始查询环境与 worker 隔离环境分开。独占模式权限不足即停止（2026-10-18 用户授权的唯一例外：设置 `MPS_OWNER` 后，属主为该用户的常驻 `nvidia-cuda-mps-server`/control daemon 可以留在空闲卡上，其管道定位不到或无权限时记录为 `owner_exception` 后继续；该卡须 util 0、显存 ≤ 200 MiB，MPS 客户端列表须为空，其他进程与其他属主仍拒绝；见 08 §7）；共享模式对无法定位管道的 daemon 显式记录未查询，允许 foreign 客户端，但 worker 在 CUDA 分配后必须核实自己的 PID 直接持有指定 GPU 的计算 context，无法证明则停止。已定位管道的查询失败仍报错，不能把查询失败当作空列表。详细方法见 Step 1。
- 2026-10-21 用户要求：`run_failstop_e2e.py --shared-gpu-ok`（默认关闭，只用于 timing）允许正式 timing 运行与其他任务共享 GPU：不做独占预检，只检查每卡空闲显存够本角色（`model_memory` 场景表，KV 按 `b_max`）；`shared_gpu_mode=true`（外来进程与回收按共享规则），`timing_valid` 保持 true，结果标 `gpu_sharing=shared`，每次 launch 前后记录外来 GPU 进程（PID、用户、命令前 120 字符、显存）；分析器接受并按 `gpu_sharing` 分组，不与独占数据混合。默认独占口径不变。见 08 §9。
- kill 后按 GPU UUID 采样残留进程及设备显存。`gpu_reclaim_s` = kill 已发出到目标四卡均无本次残留进程、显存回到启动前基线允许范围并稳定的时间。新 worker 必须等待此条件，超时则该轮失败，不启动新进程掩盖回收问题。
- `gpu_reclaim_s` 作为 `rejoin_join_s` 的回收子项记录完整时间区间；若回收与 45 s 修复等待重叠，只把 rejoin 就绪请求之后尚未完成的 `reclaim_wait_s` 计入 join 墙钟等待，禁止重复相加。每卡值与四卡最大值均保存。

## 6. 迁移、内存与正确性合同

### 6.1 规划与传输

1. 本地 `src==dst` 拷贝不计入链路 L、GPU 发送 S 或接收 D 负载，仍执行必要本地操作并记录实际字节、时长。
2. 候选来自具有目标分片覆盖的存活 GPU 及目标节点主机库。需要支持残余旧 TP4、EDP0 TP2、EDP1 TP4、主机的混合覆盖；不能把不完整 TP4 当作完整源布局。专家身份包含 global expert id；KV 包含 request id、层、头/分片和有效长度。
3. 主机代价 `bytes / bw + latency`，不占 GPU 发送负载 S，计入目的 D 和每节点主机聚合上限 M；沿用原带宽感知贪心，不新增算法。profile 实测各卡 H2D、每节点 4/8 卡并发 H2D、机内和跨机 P2P。
4. H2D 在目标 rank 专用 stream 异步执行，与 NCCL 传输共同进入依赖和完成协议；不会让两种来源竞争写重叠片段。
5. 每节点独立 CPU owner 持有一份共享 mmap，每 worker 注册 pinned；检查 RAM、共享空间和加载峰值，禁止每 worker 持有完整权重副本。退出只清理本任务资源。
6. 每事件、每条链路（含 H2D/本地）记录实际字节与提交到完成的耗时、有效吞吐；该耗时包括排队。若共享批完成事件，明确 `completion_granularity=batch`，不得写成独占链路活跃传输带宽。模型数据与控制字节分开。
7. 两模式在相同快照和 profile 下，按稳定设备标识归一化后迁移计划逐项一致；生产运行因时间/KV 历史不同，不要求两次独立运行产生完全相同 KV 计划。缓存键包含 membership、epoch、实际 rank 映射并失效旧计划。

### 6.2 KV、内存及参考实现

- 当前静态推理 KV 为按头切分的展开 K/V，不使用动态 latent 后端。四卡故障后 EDP0 全部在途请求从原 prompt + 已提交生成历史重新 prefill；EDP1 KV 保留。放不下的请求按原 FCFS 顺序回队首，不能丢请求或重置提交时间。
- 扩容：EDP0 TP2 服务与目标权重/KV 搬运异步重叠，稳定前缀快照 + 切换前增量；最终在一致边界切换 TP4。必须检查峰值内存，不够时按接纳倒序把在跑请求驱逐回队首并记录事件，直到预算满足；不静默停服（2026-10-18 用户确认，原为报错）。
- 缩容与扩容迁移窗口允许短暂源/目标布局共存；稳态每卡仅一套权重。缩容完成释放旧 TP4，扩容完成释放 TP2，清除释放对象的缓存引用；每卡按 dtype/形状核对理论权重字节。备用 KV 不按 Lmax×batch 常驻，只保留当前需要的状态。
- Admission 统一预留已标定切换峰值及安全余量。阶段 A microbatch=1 只验证正确性，不出服务吞吐结论；阶段 B 才加入固定槽位批量服务。
- 两模式都要求同布局、同历史、同输入/batch/order 的 logits 严格逐位一致。权重参考独立加载 checkpoint；KV 参考从切换前快照独立映射，不调用待测 planner 来构造期望。参考单独运行，不在测量时多驻留一套模型。不要求 TP2 与 TP4 跨布局 logits 逐位相同；出现不确定性则报告失败，不自动放宽到容差。
- DeepSeek-V2-Lite 使用 native router；优先使用已有参数关闭人工路由覆盖。若须改 router 算法或模型行为，先报告并确认。

## 7. 阶段 B 请求、注入及输出协议

固定离线请求集全部提交，FCFS 接纳；按各副本当前可用容量分配，EDP0 停服期间容量为零。每副本固定最大槽位，每个 decode step 后释放完成请求的 KV 槽并补入队首请求。支持逐槽位置、有效长度和 padding mask；同一副本 dense DP 必须保持 EP collective 序列一致，空分支执行必要空前向。采用 full prefill，不做 chunked prefill 和正常运行的抢占；故障回队是专门恢复语义。

数据为用户在阶段 A 后确定的 ShareGPT 子集，输出长度不超过 256，真实 greedy，固定目标长度忽略 EOS；不截断输入冒充筛选。先独立无故障 TP4 标定，选取约 108 s 的工作量，再冻结请求 ID、顺序、token、文件 SHA256、槽位预算与 profile；正式无故障 5 次与初始标定区分。

`plan.json` 必须使用 `v2-failstop`。下例 `250` 仅示范 N=1000，生成器实际写入 `ceil(0.25*N)`：

```json
{
  "version": "v2-failstop",
  "request_file_sha256": "<实际请求文件的 SHA256>",
  "events": [
    {
      "id": "fail", "type": "fail",
      "anchor": {"kind": "completed_count", "value": 250},
      "replica": "EDP0",
      "coords": [{"etp": 0, "ep": 0}, {"etp": 1, "ep": 0},
                 {"etp": 0, "ep": 1}, {"etp": 1, "ep": 1}]
    },
    {
      "id": "rejoin", "type": "rejoin",
      "anchor": {"kind": "after_event_seconds", "event": "fail", "seconds": 45},
      "wait_for": "shrink_done"
    }
  ]
}
```

`fail` 顺序为施加故障 → 发布通知 → 恢复；原始 kill 发出、退出确认、通知到达分别记录。`t_fail` 使用控制器施加故障命令发出的时刻并明确语义；4 个 PID 的实际 kill/exit 时刻单列。`t_rejoin_due=t_fail+45s`；实际 rejoin 需 shrink_done 且回收条件满足，不得提前 spawn。区分计划到期、前置就绪、rejoin 请求、spawn 与 16 world ready；delay 按区间并集计算，不将重叠等待重复求和。

统一命名：`t_rejoin_request=max(t_rejoin_due,t_shrink_done)`，此时进入 join 流程并允许等待回收；`t_rejoin_start` 是所有条件满足后真正开始回归/spawn 的时刻。`rejoin_join_s=t_world16_ready-t_rejoin_request`；`reclaim_wait_s=max(0,t_reclaim_done-t_rejoin_request)`；`rejoin_delay_s=t_rejoin_start-t_rejoin_due`。额外控制/调度延迟单列；emulate 无实际 GPU 回收子项，标记 not_applicable。这样保留完整 kill→回收的 `gpu_reclaim_s`，但不把修复等待中已完成的回收时间再加一遍。

每轮独立输出 `events_actual.json`，至少包括：

- 计划锚点、实际时刻、触发时 completed_count、request/profile/plan hashes、round/launch id、故障模式、world epoch 和 rank_map。
- fail、通知、abort、12 world ready、权重/KV 恢复、shrink_done、TP2 first token、rejoin due、每卡回收完成、spawn、16 world ready、扩容迁移、cutover、TP4 first token 的开始/结束时刻。
- 每 GPU 的 KV_used、权重/峰值显存；real 的故障前 KV_used 用独立 CPU 控制面保存的最后提交步快照，标明采样时间和 age，不能声称从死进程读取瞬时值。
- `gpu_reclaim_s`、`reclaim_wait_s`、`abort_s`、`rebuild_s`、`rejoin_join_s`、`rejoin_delay_s`、EDP1 暂停、各项顺延原因及区间。控制器统一单调时钟；跨机本地时钟记录校准误差，禁止直接相减未校准时间。

## 8. 正式矩阵与统计口径

矩阵：WeaveTP emulate ×5（一次 launch 连续五轮）、WeaveTP real ×3（每轮单独 launch）、无故障 TP4 ×5、固定降级 EDP0 TP2 + EDP1 TP4 标定 ×3。配置、profile、请求哈希、预热规则保持一致；保存实际顺序、launch id、轮号，不能隐去连续轮与独立启动的区别。

| 指标 | 定义 |
|---|---|
| 逐秒吞吐 | 各副本及全局成功提交的新增 token；重 prefill、padding、空前向、重放 token 不计新增 |
| shrink TFS | fail → EDP0 TP2 首个正确 token |
| shrink TTP | TP2 首个 token → 达到固定降级标定吞吐的 95% |
| expand time / expand TTP | 实际 rejoin → TP4 ready；TP4 ready → 达到故障前 10 s 全局均值的 95% |
| full recovery | fail → 扩容后恢复到上述吞吐阈值，包含 45 s 修复间隔 |
| 恢复判据 | 5 s 滑动均值连续 3 s 达到阈值；窗口、阈值、样本有效性固定 |
| 停服与开销 | 两事件 EDP0 停服、EDP1 real 重建暂停；总完成时间与相对无故障五次均值的差；归一化有效吞吐 |
