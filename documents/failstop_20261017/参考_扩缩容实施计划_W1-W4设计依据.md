### 逐步循环（W1）
每个逻辑步：rank 0 用接纳控制器算出 `Decision`（本步各副本接纳的请求、prefill token 数、完成的请求、阶段、队首阻塞原因、是否需要 prefill 前向、切换触发），`broadcast_object_list` 到 Gloo `control_group`；所有 rank 对同一份账本应用同一决策（账本全局一致，是 KV 计划能逐 rank 本地生成的前提）。
- **前向次数**：若本步任一副本有接纳 → 所有 rank 先做一次 prefill 前向（无接纳的副本喂 1 个 dummy token），再做一次 decode 前向；否则只做 decode 前向。原因：EP=2 的 all-to-all 把同一 EP 组的副本耦合，各 rank 每步集合通信次数必须相同；分成两次前向才能按规格分别测 `t_prefill` / `t_decode`，也与模拟器"prefill 常数 a + tok/rate"的标定方式一致。
- **dummy 前向三不**（审核第 7 条）：不写 KV、不计 token、不计入 `t_prefill` / `t_decode`；其耗时记入 timeline 新字段 `t_sync`（"为对齐集合通信而做的空前向 + 等待"），字段说明里写明。`step_time = t_prefill + t_decode + t_sync + t_ctrl + t_wait`。
- **开环模式空闲等待**（第 8 条）：队列空且下一条未到达时，rank 0 决策携带 `sleep_until`，所有 rank 用墙钟真等（`time.sleep` 到该时刻，期间不做前向），不跳时间；分阶段 / 连续模式永不空闲。等待时长记入 `t_wait`，`head_block_reason=arrival`。
- **prefill 前向**：输入 `[1, S]`，S = 本副本新接纳请求的 prompt 拼接（≤ 4096，超长单条独占），逐 token 位置从 0 重新计数；注意力用显式块对角因果 bool mask `[1,1,S,S]` 走现有 `DotProductAttention`（`fused_softmax.forward_torch_softmax` 有显式 mask 时不会触发 `sq == sk` 断言）；K/V 写入该请求分配的块。prefill 末 token 即首个输出 token（`t_first`）。
- **decode 前向**：输入 `[1, T]`，T = 本副本在跑请求数，每请求 1 个 token（teacher forcing：上一步的参考输出 token），逐 token 位置 = 该请求当前长度；注意力走分页 kernel。T=0 而其他副本 T>0 时喂 1 个 dummy token。
- 请求生成满 `output_len` 个 token 后结束，块归还；`finish_step = admit_step + output_len − 1` 由账本确定，不依赖 logits。
- 每步末 `_all_ready(ok)`（MIN all-reduce）：任何 rank 的异常/提前结束先置 `ok=False` 并参与归约，随后所有 rank 一起退出（清单 §7.4 教训）。每 10 步一次设备空闲显存护栏（`torch.cuda.mem_get_info`，无额外 synchronize），低于阈值时暂停接纳并记 `head_block_reason=mem`（规格枚举之外的扩展，只作保险，正常不应触发）。
- 每步只在 decode 前向结束后同步一次（CUDA event `synchronize`，和现有 `_decode` 一样），prefill/decode 的 GPU 时间用 event 对测，控制器与广播时间用 host 计时写入 `t_ctrl`（目标 < 3 ms，事后可核；第 9 条）。
- **控制流与拷贝流分离**（第 9 条）：每步的 Gloo 广播和每 10 步的 `all_gather_object` 只走 CPU 的 `control_group`，不与 `NCCLCopyService` 的 copy/comm/unpack 流交互；切换期间的前台步只在 `_run_async_waves` 既有的 `_all_max` / `_all_ready` 之外多一次广播。
- **容量账本扣段粒度**（第 3 条）：接纳按 token 预留但物理按段（4096 token）分配，池尾最多空一段。控制器每副本有效容量 `C_eff = C − segment_tokens`（TP2 153,754 − 4096 = 149,658，TP4 372,280 − 4096 = 368,184）；切换峰值检查用段取整后的字节：`bytes(U') = ceil(U' / segment_tokens) × segment_tokens × 每 token 字节`。W6 把同一 `C_eff` 传给模拟器（HW 常数）以保证锚点一致，并在 plan.json 记 `capacity_effective_tokens_per_replica`。

### 块级 KV（W2，K1–K7）
- **块 = 64 token，段 = 4096 token**（CLI 可配）。每个布局、每个 rank 一个 `BlockPool`，池由若干**段**组成，每段一次 CUDA 分配、覆盖全部 27 层：
  `K[G, 4096, L=27, hg=4, 192]`、`V[G, 4096, 27, 4, 128]`，G = 本 rank 的 head 组数（TP2 为 2，TP4 为 1），hg = 4 头/组（TP4 一个 rank 的头数）。
  - K3：head 组最外层 + token 在层之前，使 `seg[g, t0:t1]` 对**所有层**连续 → 一个 `(K/V, head 组, token 区间)` 就是一个连续缓冲，`launch_reshard_plan` 可原地接收（`async_execution.py` 连续 dst 切片直接 recv）。
  - 第 l 层第 h 头的 K 是 `seg[h//hg, :, l, h%hg, :]` 的跨步视图；Triton kernel 接受任意 stride。
  - K1/K7：段按需分配（增长），段内块全空时释放（请求结束、压实后、cutover 后调用 `release_empty_segments()` + `torch.cuda.empty_cache()`）；备用布局的池为空（无段）。建议 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`，冒烟时复测切换时间。
  - 每段以 `nn.Parameter` 暴露为 `kv::seg_{n:04d}.key|value`，由动态 bundle 提供 `named_parameters()`，供 `launch_reshard_plan` 按名定位。
- **`BlockKVContext(StaticInferenceContext)`**：`is_static_batching()` 仍为 True（MLA 第 321–324 行的 `cache_mla_latents` 断言不会触发），`is_block_kv = True`，`key_value_memory_dict` 保持空；`max_sequence_length = 16384 + 512` 只用于 rotary 表长度（K6；`get_rotary_seq_len = max(ctx.max_sequence_length, input_len)`）。每步 `prepare_step(prefill=[(seq, len)], decode=[seq])` 生成：逐 token 位置 `[S+T]`、写入槽位表、块表 `[T, max_blocks]`、上下文长度 `[T]`、块对角 mask（跨层缓存）。
- **Megatron 钩子（最小、受 `getattr(ctx, "is_block_kv", False)` 保护，共 ≈ 15 行）**：
  1. `megatron/core/transformer/attention.py::_adjust_key_value_for_inference`：在 `if inference_context is None: return ...`（525–526）之后、静态分配之前加 `if getattr(inference_context, "is_block_kv", False): return inference_context.adjust_key_value(self.layer_number, query, key, value, rotary_pos_emb, attn_mask_type)` —— 该方法把 K/V 追加进块并返回 `(q, k, v, rotary, AttnMaskType.no_mask, None)`。
  2. `multi_latent_attention.py` 第 376 行前：`if getattr(inference_context, "is_block_kv", False): core_attn_out = inference_context.core_attention(self.layer_number, query, key, value, attention_mask, dense_attention=self.core_attention, softmax_scale=self.softmax_scale)`；prefill 段走 `dense_attention`（块对角 mask），decode 段走分页 kernel，二者按 token 顺序拼接。
  3. `multi_latent_attention.py` 891–895：`positions = getattr(inference_context, "rotary_positions", None)`，有则 `rotary_pos_emb = rotary_pos_emb[positions]`（逐 token 取行；yarn 的 `mscale` 与位置无关，逐 token 取行是精确的）。
- **分页解码注意力**（`attention_paged.py`，K4）：Triton kernel `paged_decode_attention(q[T, np, 192], pool, block_tables, lengths, scale) -> [T, np, 128]`，通过"段基址 int64 表 + 块表"直接读块、在线 softmax、fp32 累加；每层每步一次 launch（K、V 各一次 append + 一次 attention）。守卫方式照抄 `megatron/core/inference/contexts/fused_kv_append_kernel.py`（`HAVE_TRITON`、MagicMock 回退）。同文件提供纯 torch 参考实现 `paged_decode_reference`（按请求 gather，仅测试/校验），以及**回退实现**"按段分组的 split-KV 纯 torch"（每段一次按块索引读取 + log-sum-exp 合并）。
  - **自动回退**（第 10 条）：`--e2e-attention auto`（默认）在启动时做一次自检：Triton 不可导入、kernel 编译失败、或随机块上与参考实现的 max-abs 超阈值（bf16：1e-2 相对）→ 自动切 split-KV torch，`result.json.attention_impl.decode` 记 `triton | torch_splitkv` 及回退原因，无需人工介入。冒烟时同测两条路径单步时间（= M1）写入 `attention_impl.m1_step_ms`；回退时在汇报中写明与 K4 的偏差和单步时间差，不为此卡住 W2。
- **D16 映射（K5，已从 `build_inference_pg_collection` 的 `HyperCommGrid` 顺序核实）**：`use_tp_pp_dp_mapping=False` 时 rank = tp_rank + TP·dp_index，即 TP2：`tp2 = r%2, dp8 = r//2`；TP4：`tp4 = r%4, dp4 = r//4`。TP4 副本 i = ranks {4i..4i+3} = TP2 副本 2i {4i,4i+1} ∪ 2i+1 {4i+2,4i+3}，同机（node = r//8）。头归属：TP2 tp-rank j 持有头组 {2j, 2j+1}；TP4 tp-rank k 持有头组 k。
  - 2→4：rank 4i+k 从 rank 4i + k//2（副本 2i）与 4i+2 + k//2（副本 2i+1）各收头组 k（其中一个是本地拷贝）。
  - 4→2：子副本 c∈{2i,2i+1} 的 tp-rank j（全局 4i+2c'+j，c' = c−2i）从 TP4 rank 4i+2j、4i+2j+1 各收头组 2j、2j+1，只含分给 c 的请求（按 `seq` 顺序分给预留较少的子副本）。
  - 运行时用 `live._configure_request_domains` 同样的 all-gather 校验嵌套关系；`observe_parallel_groups` 的 16 卡检查照常。
- **切换前压实（K2）与"A/B 区"布局**：对源副本每个 rank，把存活请求的块按（目标副本, seq）排序，原地置换（cycle-following，一个备用块，整块跨层拷贝）。**时机与原子性**（第 4 条）：冻结接纳并通过峰值检查后，在第 s 步 decode 完成、第 s+1 步开始之前执行，期间不解码；置换是设备内拷贝（≤ 20 GB，几十 ms），完成后才更新块表（置换与块表更新对账本是一个原子操作，任何 rank 失败则 `_all_ready` 共识后整体中止），然后才发起基础波。记 `compact_done` 事件，耗时计入该次切换的 `admission_pause_s`。排成：
  `[目标 d0 的 A 区：各请求的已满块][目标 d1 的 A 区]…[目标 d0 的 B 区：各请求的开口块][目标 d1 的 B 区]…`
  其中开口块 = 每请求当前未写满的最后一块；若其空槽 < `max_delta_steps`（= `--live-max-overlap-steps`，建议 32），在 B 区为该请求再预留紧邻的下一块，保证切换期间不需要新分配。尾部空段释放。目标 rank 以相同顺序分配块，故：
  - **基础波**：权重 + 每个 `(K/V, head 组, 源 rank→目标 rank)` 的 A 区连续区间（跨段则按段切分）→ KV 任务 ≈ 2 × 2 × 16 × (1–2 段) ≈ 10²，满足"≤ 现有固定 KV 基准的 2 倍"。
  - **增量**：基础波结束后同步传 B 区连续区间（含切换期间新写的 token；多传开口块的空槽，字节 ≤ 2 块 × 在跑数 × 块字节，TP2 单卡 ≲ 1.1 GB，走机内 PCIe 可忽略）。执行方式与现有 2138–2178 的同步 chunk 一致。
  - cutover 后目标侧块表 = A 区块 + B 区块（物理不必连续，kernel 按块表读）。
  - 不再使用 `restrict_plan_sequence`；KV 计划由 `KVPlanBuilder` 每 rank 从广播账本确定性生成（`TransferOp(param_name, peer_rank, is_send, my_slice, peer_slice, task_id)`，task_id 偏移到权重计划之后），与缓存的权重计划合并为一个 `ReshardPlan` 交给 `_run_async_waves`；`collect_transfer_tasks` 对连续切片的字节计算照常。
- 验收口径：每卡 `pool.physical_bytes()` 对 `已用 token × 每 token 字节` 误差 < 10%（长段稳态采样；段粒度 283–566 MB 与块尾空槽分别报告）。

### 计划执行器与切换流程（W3）
- `PlanExecutor` 按序布防 `switches[]`：`before_admit(X)`：X（按 `anchor.seq`，避免重复 id）到达队首时冻结接纳；`after_complete(Y)`：Y 完成的那一步末尾；布防时已完成则立即。
- 触发前峰值检查（`rule.switch_budget`，`per_card_used_plus_growth`，字节按段取整；G 取 `rule.growth_steps[方向]`，默认 2→4 为 7、4→2 为 23 与模拟器一致；校准后由 `calib.json` 的实测期间波数 + 1 覆盖，plan.json 记 `growth_steps_source: "default" | "calib:<calib_version>"`，第 11 条）：扩容 `U'_TP2 × 138,240 + (U'_2i + U'_2i+1) × 69,120 ≤ 预算`；缩容 `U'_TP4 × 69,120 + U'_子副本 × 138,240 ≤ 预算`；不满足则 `phase=drain`，暂停接纳只解码。
- 缩容前限流：长段最后一条接纳后，每个 TP4 副本预留上限 `min(0.95 × 2 × C_TP2, 0.95 × 预算 ÷ (2 × 69,120) − B_max × (G + 1))`（按指令公式；`e2e_sim.pre_shrink_cap` 现为 `− B_max × g`，W6 顺带对齐，差 256 token）。
- `LiveRuntime.perform_switch(direction)`：冻结接纳 → 峰值等待 → 压实 + 释放空段 → 目标池按序分配 + `weights[next].allocate_and_poison(stream)` → 合并计划 → `_run_async_waves(decode_fn=前台步, max_wave_tasks=8192|4096)` → 权重 `finite_flag` + `audit_weight_checksums`（在准备流上算校验和，不占前台步，正式运行也保留）→ 同步增量 → **可关的校验步**（第 2 条；`--e2e-validate-cutover on|off`，默认 off）：开启时同一批 token 在源、目标各跑一步，对在跑请求逐行 `_comparison_metrics`，bf16-relative 阈值沿用 compare 的 nrmse/cosine/top1，`_all_ready` 共识，需要全部行 logits 故临时关闭 `materialize_only_last_token_logits`；这是只有 WeaveTP 付的额外一步，冒烟与 repr_4k 验收时开启，图 1 / 图 2 正式运行关闭，`result.json.config` 记录开关状态 → 指针切换 → `release_standby(weights[old])` + 源池清空 → 账本 D16 重组 → 恢复接纳。切换期间完成的请求在 cutover 时统一结算。
- 固定布局：只构建一个模型、一个上下文，不建 `StandbyWeights`、reshard 组、计划、拷贝服务；执行器不存在。固定 TP4 直接以 `--tensor-model-parallel-size 4 --expert-tensor-parallel-size 4` 加载 torch_dist 检查点（`dist_checkpointing.load` 按全局形状分片，TP 无关）；一次性审计：WeaveTP 运行中把 swap 得到的 TP4 权重 `bitwise_checksums()` 与直接加载的 TP4 比对（`--e2e-audit-direct-tp4-load`）。

### 时间序列（W4-b）
- `TimelineWriter`：rank 0 内存追加，每 200 步落盘；`mem_alloc/mem_peak` 每 10 步由各 rank 读 `memory_allocated/max_memory_allocated`（host 侧计数器，无 synchronize）经一次 `all_gather_object` 汇总，并 `reset_peak_memory_stats`；其余步填 `null`。切换的外露等待写成 `kind: "stall"` 行，保证各阶段时长之和 = 总时长。
- `SwitchEventWriter`：事件 `switch_trigger | peak_wait_start | peak_wait_end | compact_done | base_wave_end | base_done | delta_done | target_ready | cutover | source_release_done`，里程碑名沿用 nostop 的 `switch_trigger/base_done/delta_done/target_ready`；`base_wave_end` 携带现有 `wave_records` 字段（`tasks, bytes, elapsed_s, transport_s, overlap_steps, exposed_wait_s, commit_s, observed_gbps[{src,dst,gbps}]`）；字节分类沿用 `weavetp_observations.receiver_rows` 的 `weight | kv_prefix | kv_delta`。

## 数据格式

- `requests.jsonl`：沿用现有字段 `id, source, src_index, src_id, prompt_token_ids, output_token_ids, input_len, output_len, tokenizer, sha256_text`。短请求有放回抽样 → 同一 id 可在负载中出现多次；运行时以 `seq`（在 `segments[].request_ids` 拼接中的位置）标识实例。
- `workload_<name>.json`：

  ```json
  {"workload_id":"fig1_r207_s7","figure":"fig1|fig2|repr","seed":7,"arrival":"continuous|phased|open_loop",
   "segments":[{"index":0,"kind":"short|long","arrival":"continuous|phased|open_loop",
                "request_ids":[...],"arrive_s":[...]  /* 仅 open_loop */,
                "stats":{"n":..,"input_sum":..,"output_sum":..,"input_mean":..,"output_mean":..}}],
   "requests_sha256":"...","notes":{}}
  ```
- `plan.json` v2 在现有 `make_plan.py` 输出上增补：`scheduler.kv_block_tokens`、`scheduler.kv_segment_tokens`、`scheduler.kv_bytes_per_token{tp2,tp4}`、`scheduler.capacity_tokens_per_replica{tp2,tp4}`、`scheduler.capacity_effective_tokens_per_replica{tp2,tp4}`（= 容量 − 一段）、`rule.growth_steps{"2->4","4->2"}`、`rule.growth_steps_source`、`switches[].anchor.seq` 与 `.segment`、`sim_constants{HW,STEP,PREFILL,calib}`、`calib_version`。`switches` 为空/缺失 = 固定布局。
- `result.json`（rank 0）：`schema_version, method, workload_id, segments_run, totals{duration_s, input_tokens, output_tokens, generated_tokens, throughput_total_tok_s, throughput_gen_tok_s, logical_steps}, switches[{index, direction, anchor, start_wall_s, end_wall_s, switch_wall_s, overlap_steps, admission_pause_s, drain_wait_s, snapshot_tokens, delta_tokens, delta_and_commit_s, pointer_switch_s, validation_max_diff, validation_metrics, bytes{weights, kv_prefix, kv_delta}, base{…wave_records…}, peak_mem_bytes_per_card[], source_release}], requests[{seq, id, segment, kind, replica, layout_at_admit, input_len, output_len, t_arrive, t_admit, t_first, t_done}], phase_durations_s, attention_impl{"decode":"triton|torch_splitkv", "m1_step_ms":{...}}, config{args, env, git_commit, sha256{requests, workload, plan}, world_size, parallel_groups}`。
- `timeline.jsonl`：每逻辑步一行：`kind(step|stall), t, step, layout, phase(normal|throttled|drain|switching|paused_admission), gen_tokens, prefill_tokens, admitted, completed, queue_len, head_block_reason(kv|bmax|anchor|barrier|arrival|mem|none), running[], kv_used_tokens[], kv_bytes_per_card[], step_time, t_prefill, t_decode, t_sync, t_ctrl, t_wait, mem_alloc[]|null, mem_peak[]|null`。拆分定义：`t_prefill`/`t_decode` = 本 rank 真实 prefill/decode 前向的 GPU 时间（dummy 前向不计）；`t_sync` = dummy 前向与集合通信对齐等待；`t_ctrl` = 控制器 + 广播的 host 时间；`t_wait` = 切换/峰值/到达等待；五者之和 = `step_time`。

- 分支起点依赖 fetch 到 `1034a78`；本机当前无法连 GitHub，W0 设有本地 6b0a2b7 的临时起点与 rebase 方案。
- prefill 4096 token 的激活峰值（稠密分数 `[8, 4096, 4096]` fp32 ≈ 0.5 GB + MoE 分发缓冲）不属于 2.1 GB 非权重开销，须在 `mem_peak` 中确认落在 **2.0 GB 稳态余量**内（第 6 条）；超出时按请求分块算注意力（每条 ≤ 1024）而不是改 4096 上限。
- `expandable_segments:True` 改变分配器行为，5.4 / 15.4 s 的切换时间需在冒烟中复测。
- 每步 CPU 开销（Gloo 广播 + 账本 + ≈ 80 次 kernel launch）目标 < 3 ms，相对 300 ms 步时可忽略；超出时把块表/位置构造改成增量更新。
- 各副本 T 不同导致 EP all-to-all 不均衡，步时 = EP 组内最大值；逐步记录供汇总器解释。
- 固定 TP4 直接加载 grouped-GEMM 专家权重的正确性：以逐位校验和审计兜底。
- 开环到达依赖墙钟，两次运行不逐位相同，但 2% 吞吐界应成立。
- W5 的四个长输出数据集尚不在 `e2e_prep/data` 下，需人工下载后才能生成；硬校验条数不符时停下报告。
- `after_complete` 锚点用 `anchor.seq` 定位实例，避免重复 id 歧义；旧 plan 只有 `request_id` 时取该 id 的首个实例并告警。
