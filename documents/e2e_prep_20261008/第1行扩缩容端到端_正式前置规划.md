## 1. 模型、平台与常数

- DeepSeek-V2-Lite（base 版），Megatron static 路径的 MLA **解压格式** KV（D9），每 token 每卡 TP2 138,240 B / TP4 69,120 B。
- 16 卡：TP、ETP、EP 组都在机内（已用 T09 的真实通信组核实，TP2 副本 2i、2i+1 恰好合并为 TP4 副本 i，均同机）。
- 显存（十进制 GB，单卡 34.19 GB）：TP2 权重 8.835、TP4 权重 4.358、非权重开销 2.1、稳态余量 2.0；切换时接收缓冲 2.0、余量 1.0。
- 每副本 KV 容量（预留口径）：TP2 15.4 万、TP4 37.2 万 token；全集群 123 万 / 149 万（TP4 多 21%）。
- 切换时每卡给"源 KV + 目标 KV"的预算：15.9 GB。
- 单步解码约 300 ms（另有约 250 ms 的快档，原因待查，清单 M7），TP4 比 TP2 慢约 7.5%。

### 2.2 处理规则（D13、D14、T1）
- 输入：不套 chat 模板，HF tokenizer（`/data/models/DeepSeek-V2-Lite-hf`）`add_special_tokens=False`，前面加 1 个 BOS。ShareGPT 取第一轮用户消息；Sky-T1 取 system + user 消息拼接（与 `longout_profile.py` 相同）。
- 输出：参考答案同样切 token，存 `output_token_ids`；`output_len = len(output_token_ids)`。正式运行强制生成 `output_len` 步，解码输入用参考答案 token（teacher forcing），忽略 EOS，路由用 native。
- 过滤（不截断）：ShareGPT 4 ≤ 输入 ≤ 1024、4 ≤ 输出 ≤ 2048；Sky-T1 输入 + 输出 ≤ 16384、输出 ≥ 64。
- **现有长度文件只统计了 Sky-T1 的前 3000 条**，正式抽样前要对全量重新切 token（§8 S1）。

## 3. 负载切分

- **结构：短段 S → 长段 L → 短段 S**，一次扩容、一次缩容。
  - 不做多次交替：总工作量固定时，交替次数 N 从 1 增加到 8，对固定 TP2 的比值从 1.08 降到 0.83（每次缩容前都要排空 KV，代价随切换次数线性增加），对 AnchorTP 也只从 1.00 变到 1.04 [估算]。
- **横轴：长段规模 L = 600 / 900 / 1200，S = 4000 固定。**
  - L ≤ 400 时长段不够"KV 受限"，比值随随机种子大幅波动（同为 L = 400，对 Llumnix 1.22 与 1.04），所以从 600 开始。
  - **固定请求集合（D15）**：先用固定种子把 Sky-T1 过滤后的全量打乱一次，L = 600 取前 600 条，L = 900 取前 900 条……三档是嵌套的同一批请求；短段两段各取 ShareGPT 打乱后的固定 4000 条，三档共用。
- 抽样：不放回，种子 `20261009`；记录每档用到的请求编号列表与文件 sha256。
- `workload.json`：
```json
{"workload_id": "row1_sky_L600_v1", "seed": 20261009,
 "segments": [{"kind": "short", "request_ids": ["sharegpt/..."]},
              {"kind": "long",  "request_ids": ["sky_t1_17k/..."]},
              {"kind": "short", "request_ids": ["sharegpt/..."]}]}
```

## 4. 调度规则（所有方法相同）

| 规则 | 取值 |
|---|---|
| 接纳 | 严格 FCFS，不跳过队首；放进"未满 B_max 且剩余预留 ≥ 输入 + 输出"的副本中预留最少的一个，并列取编号小的 |
| KV 预留 | 输入 + 参考输出（D5）；物理上按块随生成增长（层 2，清单 K1） |
| B_max | **256**（TP2、TP4 每副本相同）。模拟中 128 → 256 对固定 TP2 的比值 1.00 → 1.06，对 Llumnix 1.27 → 1.32；扩容前短请求超出峰值时等待，代价很小 |
| prefill | 每副本每步新接纳请求的输入合计 ≤ 4096 token（激活显存受 2 GB 余量限制）；单条超过时独占一步 |
| 步进 | 所有副本同步推进，单步时间取各副本最大值 |
| 切换期间 | 暂停接纳 |
| 副本重排（D16） | 2→4：TP2 副本 2i、2i+1 合并为 TP4 副本 i；4→2：按请求编号依次分给预留较少的子副本 |
| 失败处理 | 任何"跳过 / OOM / 提前结束"判断都先在所有 rank 间达成一致（清单 §7.4 教训） |

## 5. 切换时机（`plan.json` 的生成规则）

计划只由 WeaveTP 的轨迹生成一次，所有方法执行同一份；锚点是请求事件（D3），逻辑步编号只做记录。

1. **判定长段是否值得切**：先在固定 TP2 下模拟，长段队首"因 KV 不足被挡住"累计 ≥ 200 步才切。
2. **扩容锚点** `before_admit(长段第 1 条请求)`：触发时检查逐卡峰值（下式）；不满足就暂停接纳、只解码，直到满足。
3. **缩容前限流**：长段最后一条请求被接纳之后，每个 TP4 副本的预留上限临时降为
   `min(0.95 × 2 × C_TP2, 0.95 × 预算 ÷ (2 × 69,120) − B_max × (G + 1))`（受峰值约束的方法）或 `0.95 × 2 × C_TP2`（不受峰值约束的方法）。
   不限流的话，TP4 上会持续接纳短请求、KV 降不下来，缩容会推迟数小时（模拟中观察到）。
4. **缩容锚点** `after_complete(Y)`：限流开始后，第一个同时满足以下两条的完成事件 Y：
   - 按 D16 拆分后两个子副本的预留量都 ≤ C_TP2；
   - 逐卡峰值满足：`U'_TP4副本 × 69,120 + U'_子副本 × 138,240 ≤ 15.9 GB`，其中 `U' = 当前已用 KV + 在跑请求数 × G`，G = 切换期间前台解码步数 + 1。
5. **扩容的逐卡峰值**：`U'_TP2副本 × 138,240 + (U'_2i + U'_2i+1) × 69,120 ≤ 15.9 GB`。
6. 执行器解释锚点：按顺序逐个布防；`before_admit(X)` 在 X 到达队首时冻结接纳并切换；`after_complete(Y)` 在 Y 完成的那一步末尾切换，若布防时 Y 已完成则立即切换；任何方法自身的约束不满足时暂停接纳等待。
7. `plan.json`（v2 格式沿用交接文档 §4.5，`rule` 改为）：
```json
"rule": {"qualify_kv_blocked_steps": 200, "mode": "early_expand_throttled_shrink",
         "switch_budget": {"card_bytes": 34.19e9, "w_tp2": 8.835e9, "w_tp4": 4.358e9,
                           "overhead": 2.1e9, "recv_buffer": 2.0e9, "margin": 1.0e9,
                           "check": "per_card_used_plus_growth"},
         "pre_shrink_throttle": {"factor": 0.95}}
```
模拟中代表点（L = 600）的计划：扩容在第 4000 号请求（长段第 1 条）接纳前，约第 3.5 分钟；缩容在长段第 517 条完成后，约第 63 分钟。

## 10. 风险与待定

1. **对固定 TP2 只有约 +7%、对 AnchorTP 约 +1%**，小于单步时间噪声。正式运行前必须先压噪声（M7、M8）并重复。
2. Qwen3-30B-A3B（方案 C）暂不做：粗估在长段 ≥ 1200 条时对固定 TP2 能到 1.10–1.20，但对 AnchorTP 仍约 1.0，机时约翻倍，且两台 `/data` 都放不下权重（需内存盘或新加载代码）。
3. AnchorTP 代理的 16 卡切换时长是按 8 卡历史值外推的（36 s）；改正代码后要实测（M3 时一起测）。
4. 模拟器中的 prefill 速度、KV 搬运带宽（12 GB/s）、重启的分块重新 prefill 速度都是估算，层 1 / 层 2 完成后用实测替换再生成一次计划。
