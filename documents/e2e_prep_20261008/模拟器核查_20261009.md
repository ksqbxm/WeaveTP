## 1. 墙钟分解（代表点 A：N = 1，Sky-T1 全量，S = 4000，L = 600；各方法用自己的计划）

| 方法 | 总时长 | 正常解码 | prefill | 限制接纳期解码 | 扩容前排空 | 切换中解码 | 真正停服（权重 / 控制 / KV / 重启） |
|---|---|---|---|---|---|---|---|
| WeaveTP | 97.4 min | 69.2 | 3.6 | **22.9** | 1.4 | 0.15 | 12.5 s |
| 固定 TP2 | 104.4 | 97.9 | 6.5 | 0 | 0 | 0 | 0 |
| 固定 TP4 | 106.8 | 97.9 | 9.0 | 0 | 0 | 0 | 0 |
| AnchorTP | 98.3 | 70.0 | 3.6 | 22.1 | 1.4 | 0.36 | 50.8 s |
| 重启 | 100.9 | 85.5 | 6.4 | 7.0 | 0 | 0 | 120.3 s |
| Llumnix（不切换） | 117.7 | 110.8 | 7.0 | 0 | 0 | 0 | 0 |
| Flying（不切换） | 104.4 | 同固定 TP2 | | | | | |

- 分钟数之和等于总时长（脚本断言）。固定 TP2 / TP4 没有任何切换、排空、限流类时间（脚本断言）。
- **一个周期里，排空和限流远大于迁移。** WeaveTP 缩容前有 22.9 分钟处于限制接纳状态，解码速率 398 token/s，只有正常时（773 token/s）的一半，约合损失 11 分钟。扩容前排空 1.4 分钟。真正停服只有 12.5 秒。
- **KV 占用率只有 30–45%。** 按"输入 + 完整参考输出"预留（D5），预留已满时，实际写入的 KV 平均只占容量的 30–45%。所谓"受 KV 限制"其实是受预留限制，物理显存大半是空的。这是一个人为假设，对所有方法的比值影响都很大。

多次切换（B：N = 4，输出 1k–3k，S = 2000，L = 300）时，WeaveTP 扩容前排空 8.4 分钟、限流期 21.2 分钟，正常解码只剩 14.6 分钟，对固定 TP2 0.95（输）。

## 2. 发现的问题

| # | 问题 | 影响 | 处理 |
|---|---|---|---|
| P1 | **所有方法执行 WeaveTP 的同一份计划**。对其他方法不合理：B 中重启、Flying 刚缩容就立刻再扩容（21.3 / 21.3 / 21.4 分钟连续三次切换），重启多付 2 次约 60 s 的重载 | 夸大了对重启、Flying 的优势 | 加 `plan_mode="own"`：各方法用同一规则、按自己的容量与约束生成计划 |
| P2 | **Llumnix、Flying 切到 TP4 不增加 KV 容量**（全集群 TP2 = TP4：Llumnix 都是 98 万，Flying 都是 123 万），按我们的计划强行切换只有代价没有收益 | 共用计划时对 Flying 1.14 倍，实际应等于固定 TP2（1.07）；对 Llumnix 的 1.25 倍来自"两套权重一直常驻"，不切换时它就是"少 20% KV 的固定 TP2"，有稻草人嫌疑 | 自有计划下二者不切换。上一轮"对 Llumnix 1.5–2.5 倍"的结论作废 |
| P3 | KV 预留按完整参考输出（D5）：物理占用 30–45% | 影响"KV 受限"程度、扩缩容收益与排空长度 | 需决定是否改为按需分配 + 抢占（更接近 vLLM），列为待定 |
| P4 | 单步时间不随上下文变化（微基准只测了 C = 512） | 长上下文时低估单步时间，限流期与 TP2/TP4 差别可能变化 | 已加 `kv_coef`；需跑上下文扫描（下文命令 2）后拟合 |
| P5 | 模拟器 prefill 常数（TP2 9,790 / TP4 5,341 token/s）与按微基准全部点重新拟合的结果（6,656 / 3,991）不一致 | 用拟合值后：A 中对固定 TP2 1.07 → 1.10，对固定 TP4 1.10 → 1.06 | 用 `calibrate.py` 统一从原始数据拟合 |
| P6 | 切换代价都是 KV ≈ 0 时测的（WeaveTP 扩 5.4 / 缩 15.4 s，16 卡）；KV 搬运按假设 12 GB/s 加在上面；AnchorTP 36 s 是从 8 卡外推的 | 未知，但按分解它只占总时长 0.2–0.9%，影响不了量级 | 下文命令 1 在真实 KV 负载下测 |

## 4. 真实 GPU 测量

**命令 1：带 KV 负载的完整切换周期（SL3060 单机 8 卡）。** `tools/cycle/run_cycle_grid.sh`：

- 方法：WeaveTP、AnchorTP（只关选源）、Llumnix。
- 每副本 16 条 × {8, 1024, 2048, 3072} token 的 KV（源布局约 0–6.8 GB/卡）。
- 每次运行切换 4 次（扩、缩各 2 次）。
- 记录：
  - 每次切换的墙钟、波数、期间前台解码步数与 token；
  - 暴露等待、增量 KV 与提交时间；
  - 有效进度损失（墙钟 − 期间步数 × 稳态单步）、迁移字节；
  - 每次切换的显存峰值（torch 分配 / 保留 + nvidia-smi）；
  - 切换后多少步恢复到稳态单步。

**局限：**

- 现有代码（静态 KV、所有请求等长、TP2 两个副本持有相同请求）测不了"长请求进入、陆续结束、等 KV 降下来"的**排空过程**。
- 排空时长由调度和请求寿命决定，在 GPU 上依赖的只有单步时间和 prefill 速度，这两项分别由命令 1 和命令 2 测量。
- 真正的请求级完整周期要等层 1（C1–C3）写好后跑，作为层 1 的第一项验收。
- 扩容时 TP2 两个副本是重复请求，迁移字节与真实合并不同。所以校准按源布局每卡 KV 字节拟合，不直接套用字节数。

**命令 2：单步时间随上下文变化（SL3061）。** 用已有的 `microbench_ec.py`，batch 取 16 / 32 / 64 / 128，上下文取 512 / 2048 / 4096 / 8192，拟合 `kv_coef`。

## 6. 补充：真实 GPU 上的"完整切换周期"（2026-10-09）

`tools/cycle/` 已加入切换后的连续解码段：

1. 每副本 16 条 × KV token 的长请求进入；先测 TP2 稳态单步。
2. 扩容 2→4，在真实 KV 负载下迁移。
3. 在 TP4 上连续解码 `CYCLE_HOLD_TP4` 步，代表长段和排空期。
4. 缩容 4→2。
5. 在 TP2 上连续解码 `CYCLE_HOLD_TP2` 步，代表恢复期。

每段记录墙钟、单步时间、产出 token 和显存峰值；每次切换记录墙钟、期间前台步数与 token、暴露等待、增量与提交、迁移字节、显存峰值、恢复步数。

**不能直接测的部分：** 长请求一条条结束、KV 逐步释放、等 KV 降到能缩容。

- 现有代码只有静态 KV：所有请求同长、同时开始，显存预先整块分配，结束的请求不会释放显存。
- Megatron 的动态批处理（分页 KV）需要 flash-attn，这两台机器没有装。
- 所以排空的**步数**由真实请求长度加上切换规则决定，用校准后的模拟器按真实长度回放得到；每一步的**时间**用这里在 TP4、KV 负载下实测的单步时间。
- 要在 GPU 上直接测"请求逐条结束、KV 释放、排空"，需要先实现按请求管理的 KV 与调度（代码改动 C1–C3）。
