# WeaveTP 第 1 行（扩缩容）端到端实验：进度总览

> 截至 2026-10-09。分支 `codex/standby-weight-storage`，最新提交 `e6eed36`。
> 本文汇总这一轮对话的全部进度：已定事项、实测数据、模拟结果（含已作废的）、工具与脚本、待办和待决。细节见文末的文件索引。
> 数字标注规则：**[实测]** 来自 5090 服务器；**[外推]** 由实测换算；**[假设]** 人为设定；**[模拟]** 来自 `sim/` 模拟器。

## 0. 一页结论

1. **原先的模拟比值不能直接用。** 2026-10-09 的核查（§5）发现：
   - 所有方法共用 WeaveTP 的切换计划，导致基线做了不合理的切换；
   - Llumnix、Flying 切到 TP4 根本不增加 KV 容量；
   - KV 按"输入 + 完整参考输出"预留，实际占用只有 30–45%；
   - 单步时间不随上下文变化；
   - prefill 常数与原始数据的拟合不一致。
   
   因此"对 Llumnix 1.25–2.5 倍"、"对 Flying 1.14 倍"两条结论**作废**。
2. **一个扩缩容周期里，排空 / 限流成本远大于迁移成本** [模拟]。代表点上：
   - WeaveTP 缩容前约 23 分钟处于限制接纳，解码速率只有正常的一半，约合损失 11 分钟；
   - 真正停服只有 12.5 秒，相差约 50 倍；
   - 这一点还要在真实 GPU 上验证（§8 的命令 1）。
3. **对固定布局的优势有结构上限** [模拟]。EP = 2 下 TP4 只多约 21% 的 KV，TP4 单步又慢约 7.5%，满显存时上限约 1.09 倍；现计划约 1.06–1.10 倍。
4. **多切换（交替频率高）不会自动提高优势。** 它能拉大对 AnchorTP、重启的差距（这两者切换慢），但每个周期都要付排空代价，对固定布局会变差。
5. **下一步：**
   - 先在真实 5090 上测带 KV 负载的切换周期，并测单步时间随上下文的变化；
   - 用这两份实测校准模拟器，再定端到端主图。
   - 需要用户决定：
     - 是否现在实现 C1–C3（按请求管理 KV 与调度，才能在 GPU 上直接测排空）；
     - KV 预留方式。

## 3. 实测数据（5090，十进制 GB，单卡 32,607 MiB = 34.19 GB）

### 3.1 显存与容量（EP = 2）[实测]
- 权重 + 状态：TP2 8.835 GB/卡，TP4 4.358（4.361）GB/卡。
- 非权重开销 O：TP2 1.47、TP4 2.11 GB，统一取 2.1 GB（empty_cache 之后）。
- 空闲：TP2 23.7–23.9 GB，TP4 27.6–27.7 GB（SL3060、SL3061 一致）。
- KV 字节/token/卡：TP2 138,240，TP4 69,120（MLA 解压格式，27 层，由配置推导）。
- 容量（留 2 GB 余量）：每副本 TP2 15.4 万、TP4 37.2 万 token；全集群 123 万 / 149 万（**TP4 只多 21%**）。
- 两套权重常驻：稳态 15,849 MiB（命令 B），对应全集群约 90–98 万 token。
- 切换接收缓冲：8 卡约 1.1 GB；16 卡按 2 GB [假设]。
- 切换峰值预算（源 + 目标 KV）：8 卡约 16.8 GB，16 卡按 15.9 GB/卡 [外推]。

### 3.2 单步时间 [实测，只测了上下文 512]
- 两个离散档位，与 batch 基本无关：快档 TP2 约 245–262 ms、TP4 约 265–284 ms；慢档 TP2 约 290–325 ms、TP4 约 320–348 ms。档位在一次运行中成段切换，原因不明（清单 M7）。
- TP4/TP2 ≈ 1.07–1.08；B 从 16 到 256 只慢约 5–7%。
- 按全部数据点拟合：TP2 293 ms，TP4/TP2 1.054，残差中位 19–32 ms（`sim/calib_microbench_1009.json`）。
- **随上下文的变化未测**（命令 2 补测）。
- SL3060 的 GPU2、3、6 被锁在约 2010 MHz（清单 M8）。

### 3.3 prefill [实测]
- TP2：1×1024 0.34 s，8×1024 1.19 s，1×4096 0.69 s，4×4096 2.62 s，1×8192 1.55 s；1×12288 及以上预计 OOM（非融合注意力）。
- TP4：1×1024 0.32 s，8×1024 1.85 s，1×4096 0.99 s，4×4096 3.76 s。
- 全部点拟合：TP2 0.139 s + token/6,656；TP4 约 0 s + token/3,991。模拟器原用的是 9,790 / 5,341，**不一致**（§5 P5）。
- TP2 上 1×12288 prefill 会因单个 rank OOM 导致各 rank 走上不同路径，进而挂住。教训：任何跳过、OOM、提前结束的判断都要先在所有 rank 间达成一致。

### 3.4 切换 [实测]
- 8 卡 WeaveTP（W2，小 KV）：2→4 4.61 / 4.37 s，4→2 11.84 / 12.11 s；波数 6 / 22。
- 16 卡 T09 WeaveTP（W2，KV ≈ 0，1 次 launch）：2→4 5.125 / 5.649 s，4→2 16.644 / 14.066 s。模拟器取扩 5.4 s（期间解码 6 步）、缩 15.4 s（22 步）。
- 16 卡配置（`compare_weavetp_16gpu.py`）：WeaveTP 扩容每波上限 8192、Fixed 4096（WeaveTP 每波搬的量是 2 倍，6 波对 12 波）；缩容都是 4096、22 波；WeaveTP 开选源。
- 历史 8 卡代理（KV ≈ 0）：Llumnix 1.34 s，Flying 0.79 s，AnchorTP 20.26 s（当时误开了选源），WeaveTP（历史）9.59 s。
- AnchorTP 16 卡 36 s、期间 24 / 44 步 [外推]，待实测。
- 重启加载：进程启动到加载完约 35 s [实测近似，页缓存可能是热的]。
- `MAX_OVERLAP_STEPS=1` 的含义（代码核对）：每波解码 1 步后等这一波传完；AnchorTP 代理切换期间也在解码。

### 3.5 EP = 1 [实测，已否决]
- 权重 TP2 16.31 / TP4 8.09 GB；全集群容量 TP2 约 83 万、TP4 约 127 万（+53%）。
- 单步 TP2 383–392 ms、TP4 407–422 ms，比 EP = 2 慢 1.35–1.55 倍。
- 切换：扩 9.6–13.1 s，缩 27.9–32.1 s，波数 11 / 42；迁移正确，逐位审计通过。
- 切换显存峰值：两套常驻 29,071 MiB，释放 + 审计 31,021 MiB，留给 KV 只有 0.7–2.7 GB。
- 重算后对固定 TP4、重启会输（0.93–0.97），机时约翻倍 → 保持 EP = 2。

### 3.6 数据画像 [实测，旧的长度文件]
- ShareGPT：8.3 万条可用（过滤后），输入中位 145，输出中位 123。
- Sky-T1：只统计了前 2,931 条；输出中位约 3.3k，均值约 4.1k；输出 1k–3k 的占约 44%。
- 正式抽样前要对全量重新切 token（S1，脚本已写好，§8）。

### 4.2 收益分解（相对固定 TP2）
- 现设计 1.060；切换零代价 1.052（放宽约束后计划变了，反而略低）。
- TP4 单步与 TP2 一样快时的上限：1.085–1.096。
- 结构上限：TP4 多 21% 的 KV ÷ TP4 单步慢 7.5% ≈ 1.13（只在 KV 受限时段），平均到全程约 1.09。

### 4.3 AnchorTP（切换级）
- 每次切换的额外停顿：WeaveTP 扩 3.8 s / 缩 7.9 s，AnchorTP 28.4 / 20.7 s（相差 7.5 倍 / 2.6 倍）。
- 端到端吞吐只差约 1%：一扩一缩一共多停约 37 s，而一次运行约 99 分钟。
- TTFT、逐请求 TPOT 也拉不开：P99 TPOT 都约 963 ms；最大 token 间隔 0.96 s 对 1.51 s。
- 更正过的说法："AnchorTP 切换期间前台全停"不对，按原复现它每波仍解码 1 步。

### 4.4 交替次数 / 频率（共用计划）
- 总工作量固定、N 从 1 到 8：对固定 TP2 从 1.08 降到 0.83。
- 长输出 1k–3k、N = 4、周期约 15–20 分钟：
  - 现设计：对固定 TP2 0.94–0.98；
  - 本卡头复用（目标 KV 复用本卡已有的头，峰值约 1.5 倍源 KV）：1.01–1.04；
  - 对 AnchorTP（公平，也给它复用）约 1.045，对重启约 1.15。
- 长输入数据（gov_report）周期可以缩到 7 分钟，但 TP4 prefill 慢，对固定 TP2 输。
- 周期最短受长请求寿命限制：输出 4k、每步 0.3 s，一条要活约 20 分钟。

### 4.5 显存压力（每卡可用显存 34 / 28 / 24 / 22 GB，共用计划）
- 对固定 TP2 1.07 → 1.10 → 1.20 → 1.26；对固定 TP4、重启趋近 1.0；对 Llumnix 1.25 → 2.5*（作废，见 P2）。

### 4.6 EP = 1、staged、限制显存等敏感性
见规划 §11、§12、§13、§14。staged 权重与问题 2 冲突；staged KV 只在显存紧或多切换时有用。

## 6. 关于"分段 / 流式 / staged KV 传输有没有用"（统一说法）

| 机制 | 改变的是 | 结论 |
|---|---|---|
| 流式 / 分段**传输** KV（边解码边搬、分波搬） | 迁移时的停服时间 | 现设计已经是"稳定前缀 + 增量"、分波、期间解码。停服每周期只有约 12 s，再快也只影响约 0.2%，**没用** |
| staged KV（峰值 = max(源, 目标)，切换点前释放源 KV） | 切换时的显存峰值 → 排空深度 | 只切 1 次时无用（1.06 → 1.05）；多切换时有用（0.97 → 1.06）。但要求切换点前释放源 KV，与问题 2 冲突，**不采用** |
| 本卡头复用（目标 KV 复用本卡已有的那部分头） | 显存峰值从约 2 倍源 KV 降到约 1.5 倍 | 与问题 2 兼容；多切换时对固定 TP2 从 0.95 升到 1.01–1.03。需要层 2 以"头组"为分配粒度，作为候选改动 C11，**待定** |
| 按请求管理 KV 与调度（C1–C3） | 不是"传输"，是端到端运行时本身；请求结束才能释放 KV | 正式实验本来就需要；也是在 GPU 上直接测排空的前提 |

一句话：**影响结果的是排空，而排空取决于切换时显存峰值的规则、请求寿命和 KV 预留方式，与 KV 传得快慢无关。**

## 13. 补充：缩容时机规则对比（2026-10-09，`sim/shrink_rule_eval.py`、`.log`）

三种规则，都是各方法按自己的计划切换，逐请求（C2）：
- **throttle**：长段全部接纳后，限制接纳，等 KV 降到能缩容。
- **after_long**：长段请求全部完成后才缩容，期间不限流。
- **after_long + 屏障**：分阶段负载，下一段要等上一段全部完成才开始。

| 34 GB，相对固定 TP2 | throttle | after_long | after_long + 屏障 |
|---|---|---|---|
| N = 1，L = 600 | **1.072** | 1.015（一直没缩容） | 1.013 |
| N = 1，L = 1200 | **1.067** | 1.030（一直没缩容） | 1.028 |
| N = 4，1k–3k | 0.950 | **0.991** | 1.000（不切换） |

24 GB 时 N = 4：throttle 0.848 / after_long 1.033 / 屏障 1.018。

**结论：**
- "排空"的长短确实取决于切换规则，但换成"长段完成后再切"并不能把优势拿回来。
- TP4 只在长请求排队、KV 不够用的那段时间有收益。长段全部接纳后剩下的是长请求的长尾（最长 16k 输出，约 80 分钟），任何规则都要为它付出代价：
  - 要么限制接纳（throttle）；
  - 要么留在 TP4 上跑短请求（after_long，单次运行中长尾比短段还长，结果一直没缩容）；
  - 要么所有方法一起空等（屏障）。
- 只切一次时 throttle 最好；多次切换时 after_long 更好。

## 15. 切换完全免费时的理论上限（2026-10-09，`sim/free_switch_bound.py`、`.log`）

**解析上限。** 设：
- 长相（受 KV 限制）中，TP4 比 TP2 快 p = KV 容量比 ÷ TP4 单步变慢倍数（1.075）；
- 短相（受 B_max 限制）中，TP2 比 TP4 快 q：B_max 每副本相同时 q = 2 × 1.075，每卡相同时 q = 1.075。

切换免费时，最优策略是每一相都用较快的布局。对"最优固定布局"的上限，在两种固定布局一样快时取到。

| 每卡显存 | KV 容量比 | 对固定 TP2 上限（全程受 KV 限制） | 对最优固定布局上限（B_max 每副本 / 每卡相同） |
|---|---|---|---|
| 34.19 GB | 1.21 | **1.13** | **1.11** / 1.05 |
| 30 GB | 1.26 | 1.17 | 1.15 / 1.05 |
| 28 GB | 1.30 | 1.21 | 1.18 / 1.06 |
| 24 GB | 1.40 | 1.31 | 1.24 / 1.06 |
| 22 GB | 1.49 | 1.39 | 1.29 / 1.06 |
| 20 GB | 1.63 | 1.52 | 1.36 / 1.07 |

**按当前负载模拟（切换 0 秒、没有峰值约束；三种缩容规则里取最好）。** 满显存时：对固定 TP2 1.06，对固定 TP4 1.05–1.08，对最优固定布局 1.05–1.06。实际 WeaveTP 是 1.05–1.07，二者基本相同。

模拟值在个别点上略低于实际 WeaveTP，这说明计划规则本身不是最优的，并不说明切换有负收益。

**结论：**
- 满显存时，即使切换完全免费，对固定布局的上限也只有约 1.11–1.13。排空、迁移、长尾这些系统开销加起来只占几个百分点，优化掉也到不了 1.3 倍。
- 要到 1.3 倍，"TP4 多出的 KV"必须达到约 1.4 倍以上：每卡显存 ≤ 24 GB，或者换权重占比更大的模型。
- 如果 B_max 改按每卡计算（TP4 副本可放 512 条），固定 TP4 在短段也不吃亏，对最优固定布局的上限只有约 1.05–1.07。

### 17.3 建议：容错（第 2 行 fail-slow、第 3 行 fail-stop）的横轴

交接文档原设计：横轴是一段时间窗口内的故障事件次数（2 / 4 / 6 / 8），事件是可恢复故障；纵轴是端到端有效吞吐。

**为什么容错可以用"事件次数"，扩缩容不行：**
- 扩缩容是可选的，固定布局可以完全不切换、不付代价。所以切换越多，对固定布局越不利。
- 故障是强制事件，每种方法都必须处理：重启、AnchorTP、Llumnix 式迁移都要付各自的恢复代价。WeaveTP 每次恢复的代价更低，事件越多差距越大。这正是这类横轴的本意。

**建议的横轴（主图 + 敏感性）：**

| 图 | 横轴 | 纵轴 | 预期趋势（定性，尚未模拟） |
|---|---|---|---|
| 主图（两行各一张） | 时间窗口内的故障次数 2 / 4 / 6 / 8 | 端到端有效吞吐（归一化） | 对重启、AnchorTP 的优势随次数单调变大。每次 fail-stop 代价含：降级布局重建（F4）、坏卡上 dense 分片从同节点副本取、专家分片跨机取（F3）、放不下的请求驱逐后重新 prefill（F1、R1）、约 5 分钟后扩回（F7，再选源一次） |
| 敏感性 1 | 故障发生时每卡 KV 量（低 / 中 / 高，或长段内 / 短段内） | 每次故障的有效进度损失 | KV 越多，重启式恢复（丢弃 KV 重新 prefill）越贵，WeaveTP 保留与迁移 KV 的优势越大 |
| 敏感性 2（fail-stop） | 跨机带宽，或注入的背景流量 | 恢复时间 | 专家分片只能跨机取（约 2.9 GB/s），按带宽选源的价值最明显 |
| 敏感性 3（fail-slow） | 慢卡的减速倍数（例如 0.8 / 0.6 / 0.4 倍速），或持续时长（如 5 / 10 / 20 分钟） | 端到端有效吞吐 | 同步步进下一张慢卡会拖慢整个节点。减速越重、持续越久，及时撤离越划算；需要定撤离门槛 S |
| 可选 | 故障位置（与源同机 / 跨机） | 恢复时间 | 体现"机内副本 vs 跨机副本"的选源 |

- AnchorTP 代理要补最小重载数据量（CMM，清单 L3）。
- 重启要实现分块 prefill（R1）。
- fail-slow 的施加方式需要问管理员：锁频要 root；MPS 属于别的用户（F8）。
- 故障事件也用请求事件作锚点，离线排好。

## 18. 为什么 TP2 / TP4 差别这么小，以及重启的条件（2026-10-10，`sim/restart_and_scenario.py`、`.log`）

**根因是硬件和推理引擎实测出来的性能特征，不是模拟器的算术错误。**

在 5090（PCIe 互联，没有 NVLink）+ Megatron static 推理（local 实现，没有 flash-attn）上，TP4 除了 KV 容量以外，各方面都不比 TP2 强：
- 解码单步：TP4 比 TP2 慢约 7.5%（实测，上下文 512），单步约 300 ms，与 batch 基本无关。按显存带宽估算，读完权重只要约 5 ms，所以单步时间主要是固定开销和 PCIe 上的 TP 通信。
- 每副本 prefill：TP4 1×4096 0.99 s，TP2 0.69 s（实测）。全集群 prefill 速度 TP2 约 7.8 万、TP4 约 2.1 万 token/s。
- KV 容量：TP4 只多 21%。
- 因此 TP 度对吞吐几乎没有影响，切换的理论上限约 1.1 倍（§15）。

**换场景验证：超长输入（合成，输入 8k–140k，输出 300–1000），34 GB。**

| 输入长度 | 全集群可并发 TP2 / TP4 | 对固定 TP2 | 对固定 TP4 |
|---|---|---|---|
| 8k–16k | 96 / 116 | 0.90–0.96 | 1.15–1.28 |
| 30k–50k | 24 / 36 | 0.87 | 1.05–1.09 |
| 60k–75k | 16 / 20 | 0.85–0.86 | 1.04–1.06 |
| 80k–100k | 8 / 16 | 1.07–1.14 | 1.03–1.06 |
| 100k–140k | 8 / 12 | 0.96–0.97 | 1.01–1.07 |

长输入以 prefill 为主，TP4 的 prefill 慢很多，即使并发翻倍，对固定 TP2 也大多是输。另外，超过 12k 的 prefill 在没有 flash-attn 时会 OOM，真机上还需要分块 prefill。

**重启的模拟条件：**
- 切换时所有在途请求停下，丢弃 KV。
- 重新加载 35 s：实测近似，页缓存可能是热的；没算两机 torchrun 重启、NCCL 初始化、冷读盘。
- 然后把所有在途请求的"输入 + 已生成"重新 prefill，速度按 6,000 / 4,400 token/s 每副本（假设），期间没有任何解码。
- 整个过程全部计为停服。不受切换峰值约束；缩容同样要等子副本放得下。

**重启敏感性（N = 1，L = 600，34 GB）：**

| 重载时间 | 重新 prefill 速度 | 每次切换停服 | WeaveTP ÷ 重启 |
|---|---|---|---|
| 35 s | ×1.0 | 68 / 52 s | 1.036 |
| 60 s | ×1.0 | 93 / 77 s | 1.045 |
| 120 s | ×1.0 | 153 / 137 s | 1.065 |
| 35 s | ×0.5 | 101 / 69 s | 1.045 |
| 120 s | ×0.5 | 186 / 154 s | 1.074 |

重启每次切换的停服是 WeaveTP（每次多停 3.8 / 7.9 s）的 10–40 倍。但一次运行约 100 分钟只切两次，停服合计只占 2–6%，所以端到端看起来"很好"。重启的劣势应该在切换级图和容错行（故障次数多）里体现。

**切换真正有意义的场景（待验证）：**
1. **长上下文解码。** 每卡读的 KV 在 TP4 下减半；如果上下文变长后单步时间明显上升，TP4 在长上下文解码时可能反而更快。命令 2（单步时间随上下文的扫描）就是验证这一点，**优先跑**。
2. **显存紧或权重占比大**（§17.1）：KV 容量比 ≥ 1.4 时上限约 1.3。
3. **容错**（第 2、3 行）：切换是被迫的，所有方法都要付恢复代价。
4. **不成立的：** 以延迟为目标的 TP4（在这套硬件上 TP4 单步不更快）；长输入、prefill 为主的场景。

## 19. 切换有意义的场景（2026-10-10，`sim/meaningful_scan*.py`、`meaningful_seed*.py`，日志同名）

**目标：** 找一种负载，让固定 TP2、固定 TP4 各自在某一段明显吃亏，WeaveTP 同时赢过两者。

**机制：**
- 短段（聊天短请求，受 B_max 限制）：TP2 副本数是 TP4 的两倍，并发约 2 倍，TP4 吃亏。
- 长段（受 KV 限制）：TP4 能放下更多长请求，TP2 吃亏。
- 长段要做到三点：
  1. **解码为主**（输入短、输出长）：避开 TP4 prefill 慢的问题。
  2. **输出长度集中在一个窄范围**：长尾短，缩容等待少。
  3. **长度约 10–13k**：按整条请求装箱时，TP4 能多装约 29%（每副本 12 条对 31 条，全集群 96 对 124），比按容量算的 +21% 更多。
- 短段总量足够大，使短段时间和长段相当。

**模拟结果**（34 GB 满显存；合成长请求：输入 300–800、总长 12k ±10%；3 个种子的范围；各方法用自己的计划）：

| 结构 | 对固定 TP2 | 对固定 TP4 | 对 Llumnix | 对 Flying | 对重启 | WeaveTP 时长 |
|---|---|---|---|---|---|---|
| N = 1，长 240 条，短合计 20000 | 1.22–1.25 | 1.08–1.12 | 1.34–1.54 | 1.22–1.25 | 1.00–1.01 | 2.7 h |
| **N = 1，长 240 条，短合计 40000** | **1.18–1.19** | **1.17** | **1.42–1.46** | **1.18–1.19** | 1.00–1.01 | 3.1 h |
| N = 1，长 240 条，短合计 60000 | 1.14–1.16 | 1.27–1.28 | 1.36–1.42 | 1.14–1.16 | 1.01 | 3.5 h |
| N = 2，每周期长 240 条，短合计 60000 | 1.13 | 1.13 | 1.38–1.39 | 1.13 | 1.00–1.01 | 5.7 h |

- 对照：长段输出 ≥ 16k 或长度分布很宽时，长尾长、不稳定，对固定 TP4 只有约 1.0–1.1。以输入为主的超长请求时，对固定 TP2 会输（§18）。
- **对两种固定布局都约 1.17–1.19 倍**（满显存，结果稳定），超过 §15 按 +21% 算的 1.11 上限，原因是整条请求装箱的粒度效应。
- 重启仍约 1.0：只切两次。重启的劣势在切换级图和容错行体现。

**真实数据：** 输出 10k–13k 的样本，在现有长度文件（每个数据集只统计了前约 3000 条）里：
- OpenR1-Math 273 / 2912（全量约 22 万条，按比例约 2 万条）
- s1K 197 / 840
- LIMO 85 / 760
- LongWriter 92 / 2939
- Sky-T1 78 / 2931

输入中位数都在 80–120 token，解码为主。**长段改用 OpenR1-Math 中输出 10–13k 的请求**即可，样本充足。

**前提和风险：**
1. 单步时间按不随上下文变化计算（kv_coef = 0）。上下文 12k 时注意力开销未测，必须用命令 2 校准；若长上下文时 TP4 相对更快，结果还会更好。
2. TP4 在短段吃亏的前提是"B_max 每副本相同"（256）。如果按每卡相同，固定 TP4 在短段不吃亏，结果会退化。这一点要在论文里说明理由，例如每个实例配置相同的 max_num_seqs。
3. 单次运行约 3 小时，7 根柱子约 20 小时。

## 20. 为什么对重启只有约 1.01（2026-10-11，`sim/restart_vs_weavetp.py`、`.log`）

负载：长段总长约 12k、以解码为主；短段合计 40000 条；34 GB；每个方法按自己的计划。墙钟分解（分钟）：

| | 总时长 | 正常解码 | prefill | 限流期 | 扩容前排空 | 停服 | 每次切换墙钟 |
|---|---|---|---|---|---|---|---|
| WeaveTP | 183.1 | 99.1 | 21.8 | 60.4 | 1.5 | 0.2 | 6 / 16 s |
| 重启（35 s，按假设速度） | 185.3 | 103.9 | 25.2 | 53.9 | 0 | 2.3 | 78 / 57 s |
| 重启（120 s，速度 ×0.5） | 189.2 | | | | | 6.2 | 206 / 164 s |
| 重启（300 s，速度 ×0.25） | 197.4 | | | | | 14.3 | 472 / 389 s |
| 固定 TP2 | 218.3 | 189.7 | 28.6 | 0 | 0 | 0 | — |

WeaveTP ÷ 重启：1.012 / 1.034 / 1.078。

**定义核对：**
- 重启的模拟语义：所有在途请求停下，丢弃 KV；重新加载目标布局的权重；把在途请求的"输入 + 已生成"重新 prefill。整个过程没有解码，全部计为停服。
- 因为不保留任何旧状态，重启不受切换峰值约束（两套权重 + 两份 KV），这在物理上成立。
- 偏乐观的地方是常数：35 s 是单机 8 卡、热页缓存下测的；没有算两机 torchrun 重启、NCCL 建组、冷读 59 GB checkpoint；长上下文的重新 prefill 也会更慢。

**为什么只有约 1.01：**
1. 一次运行约 3 小时只切 2 次。重启每次多停约 1 分钟，合计只占 1–2%。
2. WeaveTP 是在线迁移，切换时两套权重和源、目标两份 KV 同时在卡上，受峰值约束，缩容前的限流期比重启长约 6.5 分钟，抵掉了一部分停服上的优势。

**不是"不优化的 Llumnix"：**
- Llumnix：目标布局的权重一直常驻，KV 一直少约 20%，但切换便宜。
- 重启：什么都不常驻，KV 满额，但每次切换贵。
- WeaveTP：KV 满额，切换便宜，代价是切换时的峰值约束。

切换次数少时，"每次切换贵、平时满额"（重启）在端到端上比"平时就少 20% KV"（Llumnix）划算，所以重启比 Llumnix 好很多，而且始终不超过 WeaveTP（≥ 1.00）。

**怎么体现对重启的优势：**
- 切换级图：每次停服约 1–8 分钟对 0.2 分钟以内。
- 容错行：故障次数为横轴，每次都必须恢复。
- 需要实测 16 卡、两机、冷缓存下重启的真实耗时（清单 R2）。若实际为 2–5 分钟，扩缩容行对重启约 1.03–1.08。
- 若能降低 WeaveTP 的切换峰值（本卡头复用 C11），可以缩短限流期，对重启和固定布局都有帮助。

每个周期的组成固定（长段 L 条 + 短段），周期数 N（切换 2N 次）越多，总工作量越大。34 GB，2 个种子，各方法用自己的计划。

| 长请求总长（每周期长 / 短） | 切换次数 | 对固定 TP2 | 对固定 TP4 | 对重启 | 对 Llumnix | 对 Flying | 单次时长 |
|---|---|---|---|---|---|---|---|
| 12k（240 / 40000） | 2 / 4 / 8 / 16 | 1.18 / 1.15 / 1.14 / 1.13 | 1.18 / 1.18 / 1.18 / 1.18 | 1.01 | 1.45 / 1.38 / 1.36 / 1.33 | 同固定 TP2 | 3.1 / 6.1 / 12.0 / 23.9 h |

## 26. 短段比例的文献依据（2026-10-12；只读到摘要和检索摘要，引用前必须核对原文）

**相关工作：**
- **Gyges（arXiv 2509.19729）：** 生产 trace 中长请求零星出现，专门的 TP4 实例效率很低。做法是在长请求到达时把 4 个 TP1 实例合并成 TP4，并指出 4×TP1 → TP4 会损失超过 57% 的吞吐。它是与我们最接近的工作：同样是 TP 度随请求长度变化。
- **Medha（arXiv 2409.17264）：** 动机实验中只有 5% 的长请求，就足以严重拖慢短请求（LoongServe 的短请求中位延迟升高约 30 倍）。
- **NanoCP（arXiv 2605.21100）：** 使用 1% 和 5% 的长请求比例。
- **LoongServe（SOSP'24，arXiv 2404.09526）：** 弹性序列并行，并行度随请求实时调整。
- **Infinite-LLM（arXiv 2401.02669）：** 短上下文与长上下文所需的模型并行策略差异很大。
- **Shift Parallelism（arXiv 2509.16495）：** 按流量在 TP 和 SP 之间切换；小 batch 用 TP（延迟低），大 batch 用 SP（吞吐高）。
- **Azure LLM 推理 trace（PecSched，arXiv 2409.15104 的分析）：** 约 80% 的请求输入少于 2K；输入、输出长度都呈长尾分布。
- **BurstGPT（arXiv 2401.17644）：** Azure OpenAI 服务的真实请求 trace，121 天、529 万条。

**我们的 k 对应的长请求条数占比：**
- 20k：k = 0.5 → 1.42%，1 → 0.71%，2 → 0.36%，3.3 → 0.22%，5 → 0.14%，8 → 0.09%。
- 26k：k = 0.5 → 0.85%，1 → 0.43%，3.3 → 0.13%，8 → 0.05%。

**可以这样表述：** 横轴为长请求条数占比，取约 0.1% / 0.2% / 0.4% / 0.7% / 1.4%，并引用 Gyges（长请求零星出现）和 Medha、NanoCP（1–5%）作为依据。5% 已超出我们模拟过的范围，需要补算 k ≈ 0.1 的点。

## 31. 回到横轴 = 切换次数：最优区间重复 N 次（2026-10-13，`sim/big_gain_cycles.py`、`.log`）

**设置：** 每个周期 = "最优区间"：174 条真实 8k±5% 长请求一次性突发（TP2 并发 152 → 两批、长尾不能重叠；TP4 184 → 一批；Llumnix 只放 122 条 → 两批）→ 长段全部完成后 45,000 条 prefill 为主短请求一次性密集到达（TP4 副本少 + prefill 慢）。分阶段到达（每段等上一段全部完成再提交），防止固定 TP2 用后续请求填掉第二批的尾巴。34 GB，3 种子，各方法自己的计划。

**E2. 后几个周期裁剪（T 逐周期 8k → 1.5k，短段按 T 缩放，切换越来越密）：** 对 TP2 1.51 → 1.48，对 TP4 1.43 → 1.45，对 Llumnix 1.53 → 1.50，对重启 **1.03 → 1.06**。只有对重启随切换密度上升，幅度很小；总时长 1.1 → 4.5 h。

**E4. 对照（连续到达，无栅栏）：** 对 TP2 1.53 → 1.24 → 1.11 → 1.12 衰减（§29 的尾巴填充效应），对 TP4 1.65 → 1.80 上升。

**结论（如实）：**
1. 分阶段突发 + 最优区间，每个周期都能对固定 TP2 / TP4 / Llumnix / Flying 保持约 1.43–1.53，奇数、偶数切换都成立。
2. **吞吐比不随切换次数上升。** 固定 TP2 / TP4 不为切换付任何代价，每周期优势是常数；吞吐 = 总 token ÷ 总时间，重复 N 次后比值不变。裁剪后几个周期只让对重启从 1.03 升到 1.06。
3. 对重启始终约 1.03：切换发生在段边界、在途 KV 为零，重启只付 35 s 重载；要让重启吃亏必须在 KV 满时切换，而 WeaveTP 自己的切换峰值约束（34 GB 下预算 15.9 GB）也不允许，除非实现分段 KV 传输（C 项）。
4. 以吞吐为纵轴，横轴 = 切换次数做不出上升曲线，这是物理结论，不是数据集没调好。
5. **能随切换次数上升的纵轴是延迟类指标**（平均 / p99 TTFT、排队时间）：按 WeaveTP 能跟上的速率开环到达时，固定 TP2 每个周期多出一批长请求的时间，积压逐周期累加，排队延迟随 N 线性增长，WeaveTP 不积压。当前模拟器是闭环（所有请求 t=0 可用），要加到达时间才能算；实验侧同理要用开环发送器。
6. 关于"不必模拟 / 跑完所有 iteration"：吞吐比每周期恒定，模拟和实验都只需跑 1–2 个完整周期再外推；但延迟类指标的积压是累积的，必须跑完整的 N 个周期。
